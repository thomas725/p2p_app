## 7. CI dependency gate (Low) ✅ done

The CI dependency job was `continue-on-error` on both steps and **committed result logs back into
`main`** (with errors swallowed by `|| echo`), so audit/outdated findings were informational only
and failures silently lost the artifacts.

Resolution:
- **Gate on `cargo audit` only** (hard: fail the workflow on any un-ignored advisory). It is
  already clean (exit 0), so this turns on without going red today and catches real regressions.
  `cargo outdated` stays `continue-on-error` — it exits non-zero whenever any row exists
  (incl. the unactionable table above), so a hard outdated gate would be red every day and ignored.
- **Results now uploaded as a GitHub Actions artifact** (`.github/ci-results/`) instead of
  committed to `main`. Removed the commit-and-push step, the fixed `CI Pipeline` git identity, the
  unneeded `content: write` / `checks: read` permissions, and the install-on-every-run pattern that
  could silently lose artifacts on push races.

### `libsqlite3-sys` bundled restructure — shelved permanently (not "mobile is untestable")

The proposed diesel `sqlite-bundled` restructure is **rejected**, not deferred. Reasons:
- **Android genuinely requires a bundled/compiled sqlite.** Diesel talks to sqlite through
  `libsqlite3-sys` via C-level FFI, NOT Android's Java `SQLiteOpenHelper`/`android.database.sqlite`
  or the NDK's `libsqlite3.so`. Android's platform sqlite is not reusable from Rust without a JNI
  bridge, and relying on an NDK-provided `libsqlite3.so` would add a version-dependent runtime
  dependency. Instead `libp2p_app.so` ships self-contained (see
  `apps/flutter_app/android/app/src/main/jniLibs/arm64-v8a/libp2p_app.so`) — bundling is *required*
  for the Android target.
- **The current `sqlite_bundled` feature already scopes bundling correctly.** `libsqlite3-sys`
  with `bundled` is optional and only wired into `sqlite_bundled`, which only the `mobile` feature
  pulls in. The desktop TUI links the system sqlite. Switching to diesel's `sqlite-bundled` would
  pull bundling into **every** diesel consumer — broader, not narrower. The current arrangement is
  strictly preferable, so keep it.

## 11. User-vs-device identity + contact list + (gated) calls — design + decisions (2026-09-21)

Today's identity model is device-only: one `identities` row = one libp2p keypair per install
(`db.rs:568`), and every DM/broadcast/group/session row is keyed on `peer_id` (the device). There is
no account, no "user", no device-binding, no message-history backfill. Tradeoff from that:
reconnect/rejoin loses the gap, and a roster grafted onto the peer table would be ~90% rename of
the transient mDNS-discovered peer list.

### Decisions (recorded; contacts first, calls later)

1. **Decouple *user* from *device* (user identity, 1 user → N devices).** Each user has a stable
   account identity that exists independent of any libp2p keypair. Devices bind to the user by
   **signed device-binding claims** (a "device cert" signed by the user's account key
   `sign_account(account_id, device_pubkey)`), exchanged over a lightweight `request_response`
   lane (mirroring the existing DM lane) rather than message-hijacking gossip.
2. **Signed-claim invariant — devices can never mint foreign-user bindings.** A device holding
   only its own libp2p keypair can sign claims *only within the user identity it was provisioned
   under* (e.g. its own user's sibling devices, or `account_id=itself`). It can **never** create a
   claim binding any device (itself or another) into a *foreign* user's device-set: it lacks that
   user's account key, so any such claim fails signature verification at the receiver. Hostile
   devices therefore cannot add themselves to (or vouch for) a foreign user's contact/device list.
3. **Contact list = list of *users*, not devices** (each shown once, with the user's device-set).
   Built on top of the identity layer; peers not yet resolved to a user still appear as device
   rows until their binding claim is verified. **2026-09-24 (user decision): the Peers tab is
   *replaced* by a Contacts tab in both frontends**; a single-device contact renders like today's
   peer row, and a multi-device user collapses all its bind devices into one contact row. Two-sided
   nicknames allowed: owner-side (`peer_local_nickname` / `contacts.nickname_override`) and
   receiver-side (`received_nickname` / `users.self_nickname`) may differ. Canonical shape +
   display-name rule recorded in
   `docs/2026-09-21_identity_contacts_calls_design.md` (Contacts tab section).
4. **Calls / videocalls come *after* contacts, and are **feature-gated behind a `calls` Cargo
   feature** (default-off) so default/mobile builds skip the media deps and stay lean.
5. **Group-message backfill (store-and-forward) ✅ done** (2026-09-26, own slice): gossipsub
    never replays, so an offline member misses the gap. Watermark = **`latest_group_sent_at` (max
    stored `sent_at`, computed on demand — no schema change)`; on subscribe/(re)join the node also
    subscribes the derived `group:<group_id>:backfill` topic and publishes an anonymous
    `{group_id, after}` request (`GroupBackfillRequest`). **Any** online member that knows the group
    *and* holds history strictly newer than `after` answers by re-publishing its bounded recent-N
    (`MAX_MESSAGE_HISTORY`, oldest-first, strictly-greater `sent_at`) as ordinary `GroupMessage`s on
    the **main** group topic; rows flow through the same `groups::save_incoming_group_message` so the
    `(group_id, msg_id)` unique index + `nil:` dedup absorb overlaps. Routing hazard recorded: a
    backfill topic also passes `is_group_topic`, so the swarm handler checks `is_backfill_topic`
    FIRST. Decision: gossipsub (matched design intent); watermark recomputed per request (no row).
    *Limit: works only while ≥1 history-holding member is online; there is no external
    store-and-forward.*

### Note on multi-device-per-user vs. user-identity
This item defines the *identity/contact/calls* lane. It does **not** add same-user *message
sync between devices* (a separate, larger feature; catch-up there needs ≥1 of the user's own
devices online within the gap window to serve history — same no-server-store-and-forward limit).
