## 1. Flutter First-seen column parity ✅ done (`d70b3db`)

The TUI peers table now has a sortable **First Seen** column (col 4, key `5`/`f`, header
click). Flutter's peer table still shows only Name / DM / Broadcast / Last-seen and its
`sortPeers`/`PeerSortInput` only cover columns 0-3.

Scope:
- Add a **First Seen** column to Flutter's `_PeerListState` table (`apps/flutter_app/lib/main.dart`),
  reading `MobilePeerRecord.firstSeen` (already populated via `getPeersWithStats`).
- Extend `mobile_api::PeerSortInput` with `first_seen` and `mobile_api::sort_peers` with a
  column-4 branch mirroring the TUI's `sort_peers_table` (sort via `parse_last_seen_ms` then
  `peer_id` tie-break).
- Add a Flutter sort-key constant (`_kFirstSeen`) + column header.
- Update `mobile_api::tests::{sort_peers_*}` for the new column and `KEYBOARD_SHORTCUTS.md`
  (`1-4` → `1-5`) if the TUI hint text is also touched.

Done: `PeerSortInput` gained `first_seen`; `sort_peers` col 4 sorts `first_seen` via
`parse_last_seen_ms` with `peer_id` tie-break; Flutter table got a "First seen" column and
passes `firstSeen` into `sortPeers`. Note: no `_kFirstSeen` constant was needed — the
`DataTable` column index is position-derived (4), and `_kLastSeen` survives only as the
default `_sortColumn`. Added `mobile_api::tests::sort_peers_first_seen_desc_with_id_tiebreak`.

Caveat from the TUI First-seen work: `first_seen`/`last_seen` are RFC 3339 /
`%Y-%m-%d %H:%M:%S` strings; always sort through `parse_last_seen_ms`, never string-compare.

## 3. Flutter chat auto-scroll / unread parity ✅ verified (no changes needed)

The TUI got an unread-count banner (`▼ N new message(s) — End: jump to latest`) and relies on
`is_at_bottom`/`chat_auto_scroll`. Confirm Flutter's ChatScreen has the same affordance:

- Does Flutter auto-scroll to bottom on new broadcast messages only when the user is at the
  bottom (mirroring TUI `chat_auto_scroll`)?
- Is there an unread count + "jump to latest" banner when the user has scrolled up?
- `is_at_bottom` is already exposed to Dart (`mobile_api`, `type_64bit_int` precedent); check
  whether the Flutter chat actually uses it.

Audit result (2026-09-02): full parity already holds — no code changes needed.

Flutter's `ChatScreen` (apps/flutter_app/lib/main.dart) already mirrors the TUI:
- auto-scroll-to-bottom only when `_atBottom` (main.dart:422 `if (... && _atBottom)`), exactly
  mirroring TUI `chat_auto_scroll`.
- `_onScroll` (main.dart:212-227) calls Rust `isAtBottom(...)` (exposed via `mobile_api`,
  `type_64bit_int`) — the same single source of truth the TUI uses — and resets `_unreadCount`
  to 0 when at the bottom.
- messages received while the user is scrolled up increment `_unreadCount` (main.dart:409).
- an unread banner renders `"{count} new message(s)"` with an `onJumpToBottom` button
  (main.dart:807-822) — the "jump to latest" affordance, matching the TUI banner's End key.
The `DmChatScreen` (main.dart:1321+) uses the same pattern.

## 4. Dormant `broadcasts_sent` write (Low)

Per AGENTS.md Key Decisions, `peers.broadcasts_sent` is a deliberately dormant write-only
signal: incremented at send time (`mobile_node::save_outgoing_broadcast` →
`peers::record_broadcasts_sent`) but never read by any UI (both frontends' "Broadcast"
column read `broadcast_received`).

Options:
- **Remove it fully**: drop `record_broadcasts_sent` + `save_outgoing_broadcast`'s call + the
  column + schema/migration. Cleanest, but touches the untestable mobile path.
- **Add a migration** to drop the column and migrate any history.
- **Leave as-is** (current state) and keep the documentation note.

Recommend deciding consciously; silently leaving a dead-write risks future confusion.
