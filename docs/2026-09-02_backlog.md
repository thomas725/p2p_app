# Cross-Frontend Backlog (2026-09-02)

Suggestions for future work across the TUI and Flutter frontends, plus general
hygiene. Each item is intended to be done independently and committed in
isolation. Priority order reflects value/risk.

---

## 1. Flutter First-seen column parity (High)

The TUI peers table now has a sortable **First Seen** column (col 4, key `5`/`f`, header
click). Flutter's peer table still shows only Name / DM / Broadcast / Last-seen and its
`sortPeers`/`PeerSortInput` only cover columns 0-3.

Scope:
- Add a **First Seen** column to Flutter's `_PeerListState` table (`apps/flutter_app/lib/main.dart`),
  reading `MobilePeerRecord.firstSeen` (already populated via `getPeersWithStats`).
- Extend `mobile_api::PeerSortInput` with `first_seen` and `mobile_api::sort_peers` with a
  column-4 branch mirroring the TUI's `sort_peers_table` (sort via `parse_last_seen_ms` then
  `peer_id` tie-break).
- Add a Flutter sort-key constant (`_kFirstSeen`) + column header.
- Update `mobile_api::tests::{sort_peers_*}` for the new column and `KEYBOARD_SHORTCUTS.md`
  (`1-4` → `1-5`) if the TUI hint text is also touched.

Caveat from the TUI First-seen work: `first_seen`/`last_seen` are RFC 3339 /
`%Y-%m-%d %H:%M:%S` strings; always sort through `parse_last_seen_ms`, never string-compare.

## 2. TUI Settings / Peer-info detail parity (Medium)

Verify the TUI Settings tab exposes everything Flutter's settings/details surfaces do:

- listen addresses → already renders/populates in TUI (`SwarmEvent::ListenAddrEstablished`).
- connected peer IDs / connected count → already tracked (`ConnectedTracker`).
- **identity public key** (`get_libp2p_identity`) — where does Flutter surface it? Add to TUI
  Settings if missing.
- **self nickname** (`set_self_nickname` / `get_self_nickname`) — the TUI DM tab labels
  sender as "me"; confirm a way to set/view the self nickname exists in the TUI.
- **network size / average peer count** (`get_network_size`, `get_average_peer_count`).
- **latency** (`format_latency`) display for a peer.

Goal: the TUI Settings tab and PeerInfo tab jointly cover all fields Flutter's equivalent
screens show.

## 4. Dormant `broadcasts_sent` write (Low)

Per AGENTS.md Key Decisions, `peers.broadcasts_sent` is a deliberately dormant write-only
signal: incremented at send time (`mobile_node::save_outgoing_broadcast` →
`peers::record_broadcasts_sent`) but never read by any UI (both frontends' "Broadcast"
column read `broadcast_received`).

Options:
- **Remove it fully**: drop `record_broadcasts_sent` + `save_outgoing_broadcast`'s call + the
  column + schema/migration. Cleanest, but touches the untestable mobile path.
- **Add a migration** to drop the column and migrate any history.
- **Leave as-is** (current state) and keep the documentation note.

Recommend deciding consciously; silently leaving a dead-write risks future confusion.

## 5. Guard FRB orphan `messages.dart` drift (Medium)

`apps/flutter_app/lib/src/rust/messages.dart` holds `PeerMessageStats`, which FRB never
regenerates (the Rust `PeerMessageStats` in `src/messages.rs` is NOT reachable from FRB's
`rust_input` `crate::api,crate::mobile_api,crate::mobile_node`). It has already drifted
twice (the `broadcast_sent` field needed a hand-edit this session) because its classification
flips between "generated" and "orphan".

Scope:
- Add a test that asserts the Dart `PeerMessageStats` class fields match the Rust
  `PeerMessageStats` struct fields (e.g. a Flutter `api_test.dart` test introspecting the Dart
  class, or a Rust test asserting the set of field names matches a documented list).
- Document in AGENTS.md that after any regen/refactor touching the stats surface,
  `messages.dart` must be hand-verified.
