## 4. Dormant `broadcasts_sent` write (Low) ✅ done

**Resolved** by the broadcast-stats rework: `peers.broadcasts_sent` (and its
`record_broadcasts_sent` write path) were replaced by the per-message, per-peer
`broadcast_recipients` table. The column is dropped via
`2026-09-02-000001_drop_broadcasts_sent`, the write path is now
`peers::record_broadcast_recipients`, and the persisted/UI "Broadcast" column
means broadcasts-sent-to-peer in both frontends.

Per AGENTS.md Key Decisions, `peers.broadcasts_sent` is a deliberately dormant write-only
signal: incremented at send time (`mobile_node::save_outgoing_broadcast` →
`peers::record_broadcasts_sent`) but never read by any UI (both frontends' "Broadcast"
column read `broadcast_received`).

Options:
- **Remove it fully**: drop `record_broadcasts_sent` + `save_outgoing_broadcast`'s call + the
  column + schema/migration. Cleanest, but touches the untestable mobile path.
- **Add a migration** to drop the column and migrate any history.
- **Leave as-is** (current state) and keep the documentation note.

Recommend deciding consciously; silently leaving a dead-write risks future confusion.

## 7. CI dependency gate (Low) ✅ done

The CI dependency job was `continue-on-error` on both steps and **committed result logs back into
`main`** (with errors swallowed by `|| echo`), so audit/outdated findings were informational only
and failures silently lost the artifacts.

Resolution:
- **Gate on `cargo audit` only** (hard: fail the workflow on any un-ignored advisory). It is
  already clean (exit 0), so this turns on without going red today and catches real regressions.
  `cargo outdated` stays `continue-on-error` — it exits non-zero whenever any row exists
  (incl. the unactionable table above), so a hard outdated gate would be red every day and ignored.
- **Results now uploaded as a GitHub Actions artifact** (`.github/ci-results/`) instead of
  committed to `main`. Removed the commit-and-push step, the fixed `CI Pipeline` git identity, the
  unneeded `content: write` / `checks: read` permissions, and the install-on-every-run pattern that
  could silently lose artifacts on push races.

### `libsqlite3-sys` bundled restructure — shelved permanently (not "mobile is untestable")

The proposed diesel `sqlite-bundled` restructure is **rejected**, not deferred. Reasons:
- **Android genuinely requires a bundled/compiled sqlite.** Diesel talks to sqlite through
  `libsqlite3-sys` via C-level FFI, NOT Android's Java `SQLiteOpenHelper`/`android.database.sqlite`
  or the NDK's `libsqlite3.so`. Android's platform sqlite is not reusable from Rust without a JNI
  bridge, and relying on an NDK-provided `libsqlite3.so` would add a version-dependent runtime
  dependency. Instead `libp2p_app.so` ships self-contained (see
  `apps/flutter_app/android/app/src/main/jniLibs/arm64-v8a/libp2p_app.so`) — bundling is *required*
  for the Android target.
- **The current `sqlite_bundled` feature already scopes bundling correctly.** `libsqlite3-sys`
  with `bundled` is optional and only wired into `sqlite_bundled`, which only the `mobile` feature
  pulls in. The desktop TUI links the system sqlite. Switching to diesel's `sqlite-bundled` would
  pull bundling into **every** diesel consumer — broader, not narrower. The current arrangement is
  strictly preferable, so keep it.
