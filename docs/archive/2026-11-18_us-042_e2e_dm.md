# US-042 — end-to-end encrypted direct messages (closed 2026-11-18)

> **ARCHIVED** — a historical record of completed work, kept for context.
> It is not maintained and may describe behaviour that no longer exists.
> Current documentation: [docs/README.md](../README.md),
> [`../e2e_encryption.md`](../e2e_encryption.md).

The crypto scaffolding landed on 2026-11-02 (X25519 from the install's Ed25519
identity, HKDF-SHA256 + ChaCha20-Poly1305, `msg_id` bound into the AAD, wire
and DB fields), but the send/receive paths still carried plaintext. This work
completed the wiring:

- `SealedDmBody` now also carries the US-006 reply snapshot; `seal_dm_payload`
  clears the plaintext fields on success and keeps acks, nickname-only greetings
  and DM-lane group traffic in the clear.
- `swarm_handler::send_dm` seals user traffic; `handle_request_response` opens
  the envelope before any control check, replaces the wire fields with the
  decrypted ones and sets `MessageEvent.encrypted`. Malformed or foreign
  envelopes are acked and dropped.
- The real incoming flag is persisted (`messages.encrypted`) through
  `api::save_incoming_message` / `mobile_node`, the web JSON method, and the
  Flutter node transports. `SwarmEventJson.encrypted` carries it on live events.
- Flutter renders `Icons.lock` in `MessageBubble`; the TUI keeps its existing
  `[e2e] ` marker. Both survive history reloads.

Validation: `cargo fmt --all`, `cargo ct`, strict `cargo doc`,
`cargo test --all-features`, `flutter analyze`, `flutter test`, docs link check.
The two known environmental mDNS failures remain the only test-suite failures
in this container.

Why the lane exists (and what it deliberately does not solve) is documented in
[`../e2e_encryption.md`](../e2e_encryption.md). It has no forward secrecy;
at-rest protection is a database-level concern, tracked separately.
