# AGENTS.md — operating rules for this repo

Archived history (goal, done-index, decision rationale, backlog recap, descriptive
context) lives in `docs/archive/2026-09-07_archived_agents_context.md` and the dated docs it
indexes. This file keeps only instruction-type guidance for future tasks.

## Constraints & Preferences
- **Prefer nix tooling for anything not already installed as a system tool**: use `nix-shell` and similar nix tools (e.g. `nix-shell -p python3Packages.pyyaml`) whenever something isn't installed as a system tool. Do **not** reach for `podman`/`docker` for this — only use them if there is no nixpkgs package available for what's needed.
- Toolchain: **nightly** (`rustup override set nightly` in `/home/user/project`). Every GitHub Actions workflow installs **stable** (`dtolnay/rust-toolchain@stable`) — the crate uses no `#![feature]`, so only the clippy/rustfmt lint sets can differ between CI and a dev box; treat the local nightly `cargo ct` as the stricter gate.
- All code must be clippy-clean with the project's strict pedantic config: `cargo ct` (alias for `cargo clippy --all-targets --all-features`) must exit 0 with no warnings.
- **Clippy allowance policy (post-2026-11-21 cleanup)**: hand-written non-test code carries **no** item-level clippy allows. Generated files (`src/frb_generated.rs`, `src/generated/models_*.rs`) keep their own blanket allows; test modules keep scaffolding headers (the restriction set + `used_underscore_binding`/`significant_drop_tightening` where guards are held across async blocks). Don't add new allows; use the idiom patterns the cleanup campaigns established: `String`→`&str` at the FRB boundary only where codegen accepts it, owned bytes through `impl AsRef<[u8]>` instead of an owned-then-borrowed wrapper, clone tests that consume the original as well as the clone, splitting oversized handlers instead of `too_many_lines`/`large_futures` allows, grouping FRB parameters into an input struct (`api::SaveIncomingMessageParams`) while keeping the Dart `NodeApi` signature and web JSON unchanged, grouping serialized bools into a nested struct with `#[serde(flatten)]` (`mobile_node::ChatMessageOrigin`) plus Dart extension getters so both wire shape and call sites survive, `.map_or_default(...)` instead of `.map(...).unwrap_or_default()`, `i64::try_from`/`usize::try_from(...).unwrap_or(_)` / `num_traits::ToPrimitive` for casts, and `saturating_*` for arithmetic.
- `usize_limit_to_i64` (`src/types.rs`, `crate::usize_limit_to_i64`) is the single clamp for diesel `LIMIT` clauses (messages/groups load fns); `num-traits = "0.2"` is a direct Rust dep used only for `ToPrimitive` in mobile_node/settings timestamp truncation.
- User decisions: peer click in the **Contacts** tab **keeps opening the DM tab**; message click in Chat/Group/DM **opens the sender's/partner's PeerInfo** (Log-tab clicks are a no-op — log lines have no sender).
- **Committing**: **always commit** once a logical block of work is done and it makes sense (commit early, commit often, as you work). Pushing is allowed on this machine (the "reserved for the user" rule applies to a different machine / agent setup). Every commit must credit the AI assistant as a co-author via a `Co-authored-by:` trailer naming the *actual* model and harness in use for this session. Read the name from the **live harness/runtime metadata** (the system prompt's "Your Model" section: model name + provider/harness). **Never** copy it from a prior commit, a session summary, or a template — those can be stale or name a different model. Use the form `Co-authored-by: <model> (<harness>) <noreply@...>` (or the project's established noreply address), e.g. `Co-authored-by: Big Pickle (OpenCode) <noreply@opencode.ai>`, and verify the trailer landed with `git log -1 --format=%B`.

## Code Rules (do/don't)
- **PeerInfo is a transient dynamic tab** (like DM), not a fixed tab: inserted after DMs, before Log/Settings. Dedup by peer ID.
- **The TUI Shares tab is a suffix tab appended after Settings** (`SUFFIX_TAB_COUNT` is 3): keep it last so dynamic group/DM/PeerInfo indices and the `FIXED_TAB_COUNT - 1` Groups assumption stay unchanged. `r` refreshes shares only on that tab (Settings owns `r` for relays); share events call `handle_share_event` → notice + `reload_shares()`, never a second manifest apply — the core already applied before emitting. Private grants are edited in place with `a`/`x` and `Ctrl+Up`/`Ctrl+Down`; commits go through canonical `shares::set_grant`/`remove_grant`, and a revoke's stored `user_id` is the authority (its prefilled text is confirmation only). Visibility is owner-only: `p` toggles private/public and `w` toggles anonymous writes on public shares, both through `shares::set_visibility`/`api::set_share_visibility` (`setShareVisibility` on FRB/web), which normalises `public_write` through `effective_public_write` and refuses peer-owned shares. `AppState::select_share` resets the grant cursor when the share changes so a click or wheel cannot retarget a revoke. Tests must not assume "last tab = Settings": find tabs by `TabContent`.
- **PeerInfo binding is tab-specific**: plain `i` opens PeerInfo only on the **Contacts** tab (no text input there). On **Direct/DM** tabs use `Ctrl+I` on kitty terminals (WezTerm) and `Ctrl+P` on every terminal. Settings also offers `Ctrl+P` (first connected peer by ID, else first bound device) and clickable connected/bound-device rows; `Last connected` stays informational. Both frontends order those rows by peer ID (Flutter sorts local display copies with ASCII `String.compareTo`; bound devices tiebreak on bound-at). Renderer and hit-testing must both consume `tui_render::settings_visual_lines` at the same width, so wrapped peer rows stay clickable. Bare Tab **always** cycles tabs on every tab and terminal. Shortcut bar only documents a binding where it is active.
- **Peer blocklist / mute (US-054) is enforced at the swarm boundary, never as a list filter**: `blocklist::is_blocked` gates every gossipsub message (broadcast, group and group-backfill alike), the DM / device-binding / call-signaling / file-transfer `request_response` lanes, Identify results, mDNS discoveries, `ConnectionEstablished` (immediate disconnect) and the outbound `SendDm`/`SendDeviceBinding`/`SendCallSignal`/`Dial` commands; a successful block also queues `SwarmCommand::DisconnectPeer` so a pre-existing connection is closed. Checks are **fail-open** (a DB error means "not blocked", so a broken DB never becomes a global mute) and **per peer id on purpose** — the account layer owns device grouping, the blocklist does not. TUI toggles on Peer Info with `b` (plus the `Blocked: yes/no` row); Flutter uses `PeerInfoScreen`'s app-bar action over the shared `util/blocklist.dart` helpers. Muted peers **stay listed**: the TUI Contacts table prefixes a fully muted contact with `⊘` (or marks only the blocked device sub-rows when the block is partial) via `tui_render::peers::row_is_blocked`, and Flutter's `ContactList` renders the same marker from its `blockedPeerIds` set — presentational only, never a roster filter, and `HomeScreen._togglePeerBlock` must refresh the roster so the marker follows the toggle. Any new blocklist binding needs a matching `src/web/methods.rs` arm and dispatch test.
- **Gossipsub messages are attributed to the signed publisher, not the last hop**: gossipsub runs with `MessageAuthenticity::Signed`, so in `swarm_handler`'s `AppEv::Gossipsub` arm the author is `gossipsub_author(message.source, propagation_source)`. Use that author for frontend events, group membership, synthetic group msg-ids and broadcast receipts; the `propagation_source` (relay) is used **only** for blocklist gating and attachment fetch. Attributing to the relay would show the wrong sender, make the same message get a different synthetic id on each path (breaking dedup), and ack a peer that never recorded the `broadcast_recipients` row.
- **Display-name memoization keeps the DB-backed resolution path**: don't swap the sort/render to in-memory nickname maps — `get_peer_display_name` caches the exact string it would compute (local → received → generated petname + short-ID suffix), so sort and render always agree. Invalidate exactly where nicknames change: `impl_set_peer_field!` setter macro and `peers::save_peer`; `db::set_db_url`/`reset_db_url` must keep calling `nickname::clear_display_names()`.
- **The local device is never a roster row**: `provision_my_user` writes our `peers` row (device-binding FK) and self-binds it, so `peers::load_peers`/`load_known_peers` filter the local peer ID out via `db::existing_local_peer_id` (non-generating read) and the TUI's `add_peer_to_state_list` skips `state.local_peer_id`. Otherwise a fresh install lists itself in Contacts and clicking it opens a self-DM.
- **Warm the display-name cache lazily**, on the first frame that draws the Contacts tab (`state.env.peer_names_warmed` in the render loop's draw closure), not at startup. Warm-at-startup was rejected.
- **The sort must never drop peers**: feed the whole `VecDeque` to `sort_peers_by_column` and rebuild via `HashMap<&str, PeerRecord>` — never `peers.as_slices().0` (a wrapped ring loses its second segment).
- **One canonical last-seen parser**: `fmt::parse_last_seen_ms` (space-or-T `%Y-%m-%dT%H:%M:%S`, 0 on failure) is the single source for both the TUI sort and the FRB/mobile wrapper — Dart never parses its own sort keys.
- **Keep TUI/Flutter sort parity**: Flutter sorts via Rust `mobile_api::sort_peers` (mirrors `tui_helpers::sort_peers_table`, ties on `peer_id`, descending reverses the whole `Ordering`). Don't regress to a Dart `List.sort` closure; keep `peer_list_test.dart`'s `_sortLikeRust` fake mirroring these exact semantics (lowercase name key, seen-column `parse_last_seen_ms` 0-on-failure, whole-ordering reversal).
- **`get_known_peers` (api wrapper) is a type anchor, not a live call path**: it is the only FRB-reachable reference to `MobilePeerRecord` (defined in the frb-ignored `mobile_node`). Deleting it makes the type vanish from the generated Dart and breaks `flutter analyze`. Keep it with a doc note pointing to the bulk call.
- **`apps/flutter_app/lib/src/rust/messages.dart` is a hand-maintained orphan** (`PeerMessageStats` isn't in FRB's `rust_input`; regen never touches it). Verify by hand after any change touching the peer-stats surface — including flipping the broadcast field to `broadcastSentToPeer`.
- **`broadcast_recipients` is the single per-peer "broadcast" source**: a broadcast *we* send is recorded once per connected peer (`record_broadcast_recipients`, idempotent), `confirmed_at` back-filled on ack. The "Broadcast" column uniformly means *broadcasts-sent-to-peer* in both frontends.
- **`ChatMessage.confirmed` and `ChatMessage.latency` are live decorations, never persisted**: `confirmed` is DB-computed at history load (`mark_confirmed`), `latency` is set by `save_incoming_message` from the event's round-trip time and dropped by `message_to_chat`, so a reloaded row has `latency: None` — matching the TUI, which measures it in memory only. Every frontend renders it the same way (`MessageBubble` prints it before the timestamp, the TUI prefixes it onto the line); group messages carry none.
- **Delivery receipts are DB-computed, not mirrored in memory**: `ChatMessage.confirmed` comes from `messages::confirmed_message_ids` (one batched `message_receipts` query) via `mobile_node::mark_confirmed` at history load; live `receipt` events flip the flag in Dart through `ChatMessageExt.withConfirmed` (hand-written `lib/src/data/chat_message_ext.dart` — FRB 2.13 emits no `copyWith`). Only outgoing (`sent`) messages ever tick — `mark_confirmed` never flags an inbound row even when a receipt mentions its id — and group messages hardcode `confirmed: false`. Both `HomeScreen`'s broadcast chat and `DmChatScreen` handle `receipt`; the DM screen must still forward the event to `_previousSink` so the broadcast chat below ticks too.
- **Local message deletion is a tombstone, never a retraction**: `messages.deleted_at` / `group_messages.deleted_at` are local-only `NULL`-or-timestamp columns; `mark_message_deleted` / `mark_group_message_deleted` stamp only `sent = 1` rows. Every history loader filters them, `get_all_peer_stats` drops tombstoned DMs but `broadcast_sent_to_peer` stays, and `load_group_messages_after` skips them while `latest_group_sent_at` stays unfiltered so peers cannot resend a hidden row. No wire type, `ChatMessage` field, receipt, or attachment blob changes; the single surface is `api::delete_message(id, is_group)` / `deleteMessage({messageId,isGroup})`. TUI sends must call `mark_message_sent` before a row is deletable.
- **The store-and-forward outbox holds sealed bytes only**: `dm_outbox.envelope_json` is the full sealed `DirectMessage` JSON; a sealed message has empty plaintext fields (body, nickname, attachment, reply snapshot) and only `encrypted` populated. `send_dm` queues **after** `seal_dm_payload` and only when `encrypted.is_some()` (control DMs never enter the outbox); retries re-send the stored bytes verbatim — never re-seal, and never write a readable body to this table. The unique `(recipient_peer_id, msg_id)` index is the dedup/idempotency key; the ack arm removes the row and the periodic tick prunes past `expires_at`. Recipient-side replay protection is `messages::incoming_dm_exists(peer, msg_id)` in the swarm handler, checked before the event reaches any frontend. No FRB/web surface — outbox state is internal protocol state.
- **Migration version keys are the date+time, NOT the directory stem**: two migrations sharing a timestamp (`000000`) collide silently. Use distinct suffixes (`...000000_...` / `...000001_...`).
- **`network_peers` is the single persisted source for bootstrap/relay entry points**: `src/network_config.rs` owns validation, list/add/remove and the node-start readers; every frontend submits raw text and Rust stores the canonical `Multiaddr` (relay rows must carry `/p2p/<peer-id>`). Precedence is asymmetric on purpose — bootstrap is `P2P_BOOTSTRAP` (set ⇒ wins, even empty) → persisted rows → public IPFS nodes with `P2P_PUBLIC_DHT=1`, while relays are the **union** of `P2P_RELAY` and persisted rows. Both lists are read **only at node start** (the UI and toasts say so); don't add a live reload path without changing that contract. `stored_*_addrs()` is best-effort (DB error ⇒ empty list, never a startup failure). The diesel artifacts (`schema.rs`, `models_*`, `columns.rs`) are hand-maintained here and `diesel_generate.sh` must not be run (`diesel_ext` is not on crates.io). TUI keys: `b`/`r` open a shared prompt under `InputMode::AddingNetworkPeer` + `AppState::network_peer_kind`, `x` removes the highlighted row, and the prompt branch must stay **above** the ordinary Settings shortcuts (same rule as the Contacts search box).
- **Settings "Network size" is a live connected-peer label, not gossipsub tuning**: both frontends pass the current `connectedCount` to `network::network_size_label` (FRB/web `networkSizeLabel(peerCount)`): 0–3 Small, 4–15 Medium, 16+ Large. `get_network_size()`/`get_average_peer_count()` remain DB-backed historical averages used only to choose gossipsub mesh parameters; never restore the removed startup-cached TUI field or feed the display from session history. Negative counts preserve the existing FRB/web boundary behavior (Large), but real callers pass non-negative counts.
- **Flutter Settings' "Last connection lost" label is Rust-owned**: `mobile_node::event_to_json` puts `nickname::get_peer_display_name_or_short` in `SwarmEventJson.content` on `peer_disconnected`; Home keeps it in `LiveStatus.lastConnectionLabel`, and Settings prefers it over a roster lookup (raw ID only as fallback for events without a label). Don't regenerate petnames in Dart or resolve the name from a roster that may already have dropped the peer. Web needs no extra method because it serializes the same event envelope.
- **Notification focus keys have one Rust mapping**: `notifications::conversation_key_for_tab` translates a visible chat tab into the same `broadcast` / `dm:<peer>` / `group:<id>` key that `notifications::for_message` puts on the event. `AppState::active_conversation_key` delegates to it; don't hand-build focus keys in the TUI. Peer Info and the Shares suffix tab never suppress a message. This key is distinct from `AppState::conversation_key`, whose broadcast value is `chat` because it indexes reply drafts and message cursors.
- **Reply drafts are frozen in Rust**: `mobile_api::reply_draft` (FRB/web `replyDraft`) is the only builder for the immutable `ReplyRef` sent on the wire. Flutter's `replyDraftFor` delegates to `NodeApi` and keeps only the display-only sender label and quoted header used by live bubbles/transcripts; don't reintroduce Dart-side preview, chip or sender-resolution rules. Incoming FRB snapshots are canonicalized again at persistence/wire boundaries (see `src/reply.rs`).
- **Stateful table windowing**: ratatui's `Table` + `TableState` is the "widget that allows scrolling visually" — it keeps the selected row visible. `tui_helpers::peer_table_visible_range` is the pure reimplementation that the click handler and renderer both agree on; keep them consistent.
- **Saved groups must be re-subscribed on node start** in BOTH frontends: the swarm only receives group traffic for topics it is subscribed to. TUI does it in `main_loop.rs` after `spawn_swarm_handler`; mobile does the same inside `mobile_node::start_node_impl`'s `runtime.block_on` block (added in 3b86d02). Don't drop these loops.
- **Group backfill routing precedence (§11.5)**: a backfill topic `group:<group_id>:backfill` ALSO passes `is_group_topic` (it starts with `group:`), so `handle_swarm_event` must check `is_backfill_topic` FIRST, then `is_group_topic`, then the broadcast path. `SubscribeGroup` subscribes the backfill topic and publishes `GroupBackfillRequest { group_id, after }` (`after` = `latest_group_sent_at`, max `sent_at`, `0.0` = full history); answering members re-publish bounded history (`load_group_messages_after`, strictly-greater `sent_at`, oldest-first, `MAX_MESSAGE_HISTORY` cap) on the MAIN topic, gated on `find_group` (never revive deleted groups) and `latest > after` (nothing to contribute → skip). Requests are control traffic — never persisted. Requester dedup = the normal `save_incoming_group_message` path.
- **Incoming group messages are persisted centrally by the swarm handler** (`swarm_handler::handle_group_message` → `groups::save_incoming_group_message`), so the DB is the single source of truth in both frontends. The mobile `group_message` swarm event only *notifies* the Flutter UI; `GroupChatScreen` reloads history from DB (no `save_incoming_group_message` FRB binding) and `GroupList` just refreshes counts — don't add per-screen persistence.
- **Group invites only carry a `group_id`, so materialize the group row**: `groups::ensure_group_for_invite` (used by `mobile_node::accept_group_invite`, and the TUI's GroupInvite arm which records membership then sends `SwarmCommand::SubscribeGroup`) creates the `groups` row with `display_name` = group_id when the canonical name isn't known. It is idempotent — reuses a row joined earlier by name.
- **Meshing group messages without an `msg_id` must still dedup**: `save_incoming_group_message` substitutes a stable synthetic key `nil:<fnv1a_hex(group_id|peer_id|sent_at|content)>` so SQLite's `(group_id, msg_id)` unique index (which treats `NULL`s as distinct) still stops retransmits. `GroupMessageMeta` stays as-is; the key is an internal `msg_id` on the row.
- **The caller mints the `call_id`; clients never guess one**: the TUI mints via `CallSession::outgoing`, the mobile/Flutter side mints Rust-side (`api::start_call` returns the fresh id). Every `CallSignal` echoes it (`CallSignal::new(kind, call_id)`); `CallSession::on_signal` mutates ONLY a matching-`call_id` session — stale/foreign ids are no-ops (the TUI's invite-adoption, the overlay transition, and Flutter's session filtering all rely on this). One call at a time everywhere (like the device-binding prompt/lane): BOTH frontends actively `reject` a foreign invite received during a live call so the other caller stops ringing (TUI `handle_call_event`, Flutter `_handleCallInvite`/`CallScreen`). A retransmit of the *active* call's own id is a no-op — never reject that, or you hang up on yourself and desync both sides.
- **Call signaling and media transport are un-gated** (mirrors device-binding): `behaviour.rs` `call_signaling` + `call_media`, `types.rs` `SendCallSignal` + the `StartCallMedia`/`SendCallMedia`/`SetCallMediaMute`/`StopCallMedia` commands, `calls.rs` `CallSession`/`CallState` + `call_media.rs` `MediaSession`. Both frontends ship without the `calls` Cargo feature — it stays reserved for future media deps (device audio adapters/codecs). Don't gate signaling or transport behind it. The swarm loop owns a single `Option<MediaSession>`; frames are accepted only from the pinned `call_id`/peer, `reject`/`end` clear it, and the media lane is blocklist-gated like every other `request_response` lane. μ-law + jitter buffer + mute live in `call_media.rs` (no new Cargo deps); device-level capture/playback is deliberately still a frontend adapter concern.
- **Flutter call events key on `peer_id` + echoed `call_id` (`content`)**: `call_event_json` fills `event_type`/`peer_id`/`content`(call_id); `CallScreen` owns the event sink while open (like `DmChatScreen`, restored on dispose), filters on exactly those two, forwards non-call events downstream, and auto-declines (`reject`) a second incoming invite while one session is live. The mobile send path goes through FRB-exposed `api::{start_call, send_call_signal}` wrappers over `#[flutter_rust_bridge::frb(ignore)]` `mobile_node` impls that `cmd_tx.blocking_send` a `SendCallSignal` — same shape as device-binding.
- **Files lane (§12) is receiver-driven `request_response`** (`/p2p-chat/files/1.0.0`, cbor `FileTransfer`/`FileTransferResponse` with `kind` meta/chunk/error, `FILE_CHUNK_SIZE` 1 MiB, `MAX_ATTACHMENT_SIZE` 64 MiB). `file_id` = SHA-256 of the bytes (content address); blobs live on disk under `<db>.files` (never in SQLite — `files`/`files_recipients` tables). Messages carry only the `MessageAttachment` descriptor; group/broadcast attach **by reference** so gossipsub's 256 KiB cap stays unbroken. No feature gate (un-gated, like call signaling).
- **Attachment blob GC is gated by the `attachment-gc` Cargo feature** (in `default` and `mobile`): `file_transfer::gc_stale_attachments()` sweeps `.part` partials of interrupted pulls (incomplete class) plus orphaned blobs/rows nothing references (the "overwritten"/superseded class, including blobs with no `files` row and rows whose blob vanished) — via `files::gc`/`files::GcStats`. Runs at startup in TUI (`main_loop.rs`) and mobile (`start_node_impl`), never touching in-flight transfers (active `file_id`s excluded) and honoring `files::GC_GRACE` (1 min blob age). The off-build is a `Ok(GcStats::default())` no-op — disabling the feature means the store never deletes anything. Sweeps run on startup only; a transfer interrupted mid-run keeps its `.part` until the next restart clears the in-flight map.
- **Both frontends render the canonical chip `[file] {name} ({size})`, with `{size}` produced by `files::format_file_size`** (`512 B`, `1.5 KiB`, `64 MiB` — binary units, one decimal max, trailing `.0` dropped): Rust `files::file_chip` / `render_message_body` / `render_stored_body` (hydrates DB `attachment_json` on reloads) format it, and Flutter's `_AttachmentChip` in `messages.dart` prints `MobileAttachment.sizeLabel`, which Rust fills from the same formatter — **no frontend does its own byte math**. Attachment-only messages render as just the chip. Mobile resolves blob paths exclusively through `attachment_file_path(file_id)`.
- **Flutter picks via `file_picker` 13.x — top-level `FilePicker.pickFile()`** (the `.platform` member was removed); opens via `open_filex` (`ResultType.done`/`result.message`). Both sit behind `pickFileOverride`/`openFileOverride` seams in `apps/flutter_app/lib/src/util/attachments.dart` — these are deliberately NOT `@visibleForTesting` because screens in other libraries call them (the annotation flags `invalid_use_of_visible_for_testing_member` cross-file, unlike the same-library seams in home/contact_list).
- **File shares / folder sync (share lane) reuse the files store but keep ACLs at the swarm boundary** (`/p2p-chat/shares/1.0.0`, JSON `ShareRequest`/`ShareResponse`, kinds `offer`/`list`/`manifest`/`publish`). `src/shares.rs` owns `ShareManifest`, `ShareKind`/`ShareMode`, grants, snapshots and bound-folder apply. Private ACLs resolve the connection peer to a verified `user_id` via `identity::find_user_id_for_peer` and fail closed on DB errors or unbound peers — never trust a claimed id. Public shares are read-only unless `shares.public_write`; stale `base_revision` writes are rejected. Paths are validated (no absolute paths, `..`, symlink escapes) and only previously tracked files are removed. The lane is blocklist-gated like every `request_response` lane, `shares::referenced_file_ids()` keeps manifest blobs alive through attachment GC, and `note_blob_available` emits `ShareUpdated` only once every manifest blob is local. UI/FRB/web surfaces now cover the share list/detail, grant and visibility editors, discovery, network actions and deletion publishing; share events stay JSON on the mobile event bus and are also logged by the TUI.
- **The web frontend is a display client, never a WASM node** (`docs/web_frontend.md`): `src/web/` (axum HTTP+WS) mirrors the FRB surface 1:1 as JSON methods; the `p2p_chat_server` binary runs the node in-process. Every new FRB-exposed fn needs a matching `src/web/methods.rs` arm, an entry in `src/web/mod.rs`'s no-param drift list (for zero-arg arms) and a `methods::dispatch(name, Null)` routing test asserting `invalid params:`. Build/run through `scripts/build-web.sh`.
- **TUI group leave** lives on the Groups tab: `d` arms `AppState.group_leave_prompt` (`begin_group_leave`), `y`/Enter confirms (`confirm_group_leave` → `groups::delete_group` + `SwarmCommand::UnsubscribeGroup`, closes the chat tab), any other key/Esc cancels. Popup precedence is `device_binding_prompt` > `group_leave_prompt` > call overlay > `popup`.
- **TUI local nicknames** (the name only this install shows for a peer) are edited with `n` on a **Peer Info** tab; that is distinct from the Settings-tab `n`, which edits our own nickname. Both go through `AppState::is_editing_nickname()`, which must keep covering `InputMode::EditingLocalNickname` as well as `InputMode::EditingNickname` — that mode (not a bool: `TuiRenderState` sits at clippy's `struct_excessive_bools` limit) is what tells the input-section title "Local Nickname (xxx)" from "Edit Nickname (xxx)". Submissions validate through the canonical `nickname::validate_nickname` and keep the editor open with a hint on bad input.
- **Contacts search is one matching rule, two implementations, one sort authority**: `state::contact_matches` (Rust) and `ContactListState._visibleRows` (Dart) both match a lowercased substring against the contact id, contact display name, and every device's peer id + display name — so a grouped user stays findable by a machine's peer id. Rust owns the rule; Flutter mirrors it because no FRB binding can filter a Dart list. **Filtering must happen before the Rust sort in both frontends** (TUI: `contacts` is the filtered view of `contacts_all`, re-derived by `apply_contact_search` inside `resort_peers`, never via a DB query per keystroke; Flutter: `_computeSorted` sorts only the visible subset and maps back against it), so a hidden row can never be returned by the comparator. TUI bindings: `/` opens the box, `Enter` keeps the query, `Esc` clears it; the box is checked **before** the Contacts `c`/`e`/`i` actions (`handle_contacts_action_key`) or typing those letters would place a call/expand a row. `InputMode::SearchingContacts` — do **not** add another `TuiRenderState` bool.
- **Modal TUI prompts own the keyboard through `InputMode::is_modal_editor()`**: dispatch, navigation, tab shortcuts and both input renderers all delegate to this one predicate; don't reintroduce hand-written "editing" mode lists. It covers nicknames, message edits, reactions, group create/join, dial, network-peer entry and share-grant entry. `SearchingContacts` is deliberately excluded — it is an inline filter, so Tab and arrows keep their roster meanings. Tab/`BackTab`/scroll are consumed while a modal prompt is active (the one exception is `Tab` toggling `readonly`/`readwrite` in the add-grant prompt), Enter commits in `handle_enter_dispatch` only, and a rejected network-peer address keeps its text open for correction.
- **Every actual TUI tab transition goes through `AppState::switch_to_tab`**: it calls `finalize_tab_input()`, which cancels a nickname edit and closes the Contacts search box while keeping its applied query. Keyboard, tab/row clicks, Peer Info entry and tab closes all use it; never assign `active_tab` directly. `Esc` unwinds exactly one layer: the single-slot prompts (device-binding, group-leave, delete-message) and live-call overlay own it upstream, then popup → edit → reaction → share grant → Contacts search → nickname → group prompt → dial → network peer → reply draft → message selection → Chat. Mouse-wheel events use the same arrow-key selection logic on Contacts/Groups/Settings/Shares, scroll transcripts on message tabs and are inert on Peer Info.
- **TUI mouse ownership mirrors keyboard precedence via `AppState::has_prompt_or_call_overlay()`**: device-binding, group-leave and delete-message prompts plus a live call swallow every click and wheel. An ordinary popup is click-to-dismiss even while a modal editor is active; after dismissal the modal editor swallows pointer input. `SearchingContacts` stays non-modal, so clicks still finalize the search and wheels still move the roster. Drive regressions with real `process_input_event(InputEvent::Mouse(...))`, asserting frame, state and command-channel agreement.
- **Integration DB tests use `tests/test_utils.rs`**: `mod test_utils;` plus `test_utils::{test_db_lock, with_test_db}` is the single isolated-`SQLite` setup (temp dir → set URL → migrate → closure → release/reset). Don't copy that helper into another integration-test file; each test crate gets its own static lock when it includes the module. An unverified claim must never overwrite a known user's `self_username`/`self_nickname`. At-rest protection is NOT a goal here (it's database-level — see backlog); the remaining rationale is store-and-forward/offline caching. See `docs/e2e_encryption.md`.
