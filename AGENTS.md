## Constraints & Preferences
- **Prefer nix tooling for anything not already installed as a system tool**: use `nix-shell` and similar nix tools (e.g. `nix-shell -p python3Packages.pyyaml`) whenever something isn't installed as a system tool. Do **not** reach for `podman`/`docker` for this — only use them if there is no nixpkgs package available for what's needed.
- Toolchain: **nightly** (`rustup override set nightly` in `/home/user/project`). Every GitHub Actions workflow installs **stable** (`dtolnay/rust-toolchain@stable`) — the crate uses no `#![feature]`, so only the clippy/rustfmt lint sets can differ between CI and a dev box; treat the local nightly `cargo ct` as the stricter gate.
- All code must be clippy-clean with the project's strict pedantic config: `cargo ct` (alias for `cargo clippy --all-targets --all-features`) must exit 0 with no warnings.
- **Clippy allowance policy (post-2026-09-28 cleanup)**: hand-written code carries exactly **one** clippy allow — `src/api/mod.rs` `accept_device_binding`'s `needless_pass_by_value` (FRB 2.13 has no `&[u8]` codegen input; a Dart `List<int>` must land as owned `Vec<u8>`, so the wrapper's `&device_pubkey` is irreducible). Test modules keep scaffolding headers (the restriction set + `used_underscore_binding`/`significant_drop_tightening` where guards are held across async blocks). Don't add new allows without this distinction; prefer the idiom patterns the campaigns used: `String`→`&str` at the FRB boundary only where codegen accepts it, `i64::try_from`/`usize::try_from(...).unwrap_or(_)` / `num_traits::ToPrimitive` for casts, `saturating_*` for arithmetic.
- `usize_limit_to_i64` (`src/types.rs`, `crate::usize_limit_to_i64`) is the single clamp for diesel `LIMIT` clauses (messages/groups load fns); `num-traits = "0.2"` is a direct Rust dep used only for `ToPrimitive` in mobile_node/settings timestamp truncation.
- User decisions: peer click in the **Contacts** tab **keeps opening the DM tab**; message click in Chat/Group/DM **opens the sender's/partner's PeerInfo** (Log-tab clicks are a no-op — log lines have no sender).
- **Committing**: **always commit** once a logical block of work is done and it makes sense (commit early, commit often, as you work). Only **pushing** is reserved for the user.

## Code Rules (do/don't)
- **PeerInfo is a transient dynamic tab** (like DM), not a fixed tab: inserted after DMs, before Log/Settings. Dedup by peer ID.
- **PeerInfo binding is tab-specific**: plain `i` opens PeerInfo only on the **Contacts** tab (no text input there). On **Direct/DM** tabs use `Ctrl+I` on kitty terminals (WezTerm) and `Ctrl+P` on every terminal. Bare Tab **always** cycles tabs on every tab and terminal. Shortcut bar only documents a binding where it is active.
- **Display-name memoization keeps the DB-backed resolution path**: don't swap the sort/render to in-memory nickname maps — `get_peer_display_name` caches the exact string it would compute (local → received → generated petname + short-ID suffix), so sort and render always agree. Invalidate exactly where nicknames change: `impl_set_peer_field!` setter macro and `peers::save_peer`; `db::set_db_url`/`reset_db_url` must keep calling `nickname::clear_display_names()`.
- **The local device is never a roster row**: `provision_my_user` writes our `peers` row (device-binding FK) and self-binds it, so `peers::load_peers`/`load_known_peers` filter the local peer ID out via `db::existing_local_peer_id` (non-generating read) and the TUI's `add_peer_to_state_list` skips `state.local_peer_id`. Otherwise a fresh install lists itself in Contacts and clicking it opens a self-DM.
- **Warm the display-name cache lazily**, on the first frame that draws the Contacts tab (`state.env.peer_names_warmed` in the render loop's draw closure), not at startup. Warm-at-startup was rejected.
- **The sort must never drop peers**: feed the whole `VecDeque` to `sort_peers_by_column` and rebuild via `HashMap<&str, PeerRecord>` — never `peers.as_slices().0` (a wrapped ring loses its second segment).
- **One canonical last-seen parser**: `fmt::parse_last_seen_ms` (space-or-T `%Y-%m-%dT%H:%M:%S`, 0 on failure) is the single source for both the TUI sort and the FRB/mobile wrapper — Dart never parses its own sort keys.
- **Keep TUI/Flutter sort parity**: Flutter sorts via Rust `mobile_api::sort_peers` (mirrors `tui_helpers::sort_peers_table`, ties on `peer_id`, descending reverses the whole `Ordering`). Don't regress to a Dart `List.sort` closure; keep `peer_list_test.dart`'s `_sortLikeRust` fake mirroring these exact semantics (lowercase name key, seen-column `parse_last_seen_ms` 0-on-failure, whole-ordering reversal).
- **`get_known_peers` (api wrapper) is a type anchor, not a live call path**: it is the only FRB-reachable reference to `MobilePeerRecord` (defined in the frb-ignored `mobile_node`). Deleting it makes the type vanish from the generated Dart and breaks `flutter analyze`. Keep it with a doc note pointing to the bulk call.
- **`apps/flutter_app/lib/src/rust/messages.dart` is a hand-maintained orphan** (`PeerMessageStats` isn't in FRB's `rust_input`; regen never touches it). Verify by hand after any change touching the peer-stats surface — including flipping the broadcast field to `broadcastSentToPeer`.
- **`broadcast_recipients` is the single per-peer "broadcast" source**: a broadcast *we* send is recorded once per connected peer (`record_broadcast_recipients`, idempotent), `confirmed_at` back-filled on ack. The "Broadcast" column uniformly means *broadcasts-sent-to-peer* in both frontends.
- **`ChatMessage.confirmed` and `ChatMessage.latency` are live decorations, never persisted**: `confirmed` is DB-computed at history load (`mark_confirmed`), `latency` is set by `save_incoming_message` from the event's round-trip time and dropped by `message_to_chat`, so a reloaded row has `latency: None` — matching the TUI, which measures it in memory only. Every frontend renders it the same way (`MessageBubble` prints it before the timestamp, the TUI prefixes it onto the line); group messages carry none.
- **Delivery receipts are DB-computed, not mirrored in memory**: `ChatMessage.confirmed` comes from `messages::confirmed_message_ids` (one batched `message_receipts` query) via `mobile_node::mark_confirmed` at history load; live `receipt` events flip the flag in Dart through `ChatMessageExt.withConfirmed` (hand-written `lib/src/data/chat_message_ext.dart` — FRB 2.13 emits no `copyWith`). Only outgoing (`sent`) messages ever tick — `mark_confirmed` never flags an inbound row even when a receipt mentions its id — and group messages hardcode `confirmed: false`. Both `HomeScreen`'s broadcast chat and `DmChatScreen` handle `receipt`; the DM screen must still forward the event to `_previousSink` so the broadcast chat below ticks too.
- **Migration version keys are the date+time, NOT the directory stem**: two migrations sharing a timestamp (`000000`) collide silently. Use distinct suffixes (`...000000_...` / `...000001_...`).
- **Stateful table windowing**: ratatui's `Table` + `TableState` is the "widget that allows scrolling visually" — it keeps the selected row visible. `tui_helpers::peer_table_visible_range` is the pure reimplementation that the click handler and renderer both agree on; keep them consistent.
- **Saved groups must be re-subscribed on node start** in BOTH frontends: the swarm only receives group traffic for topics it is subscribed to. TUI does it in `main_loop.rs` after `spawn_swarm_handler`; mobile does the same inside `mobile_node::start_node_impl`'s `runtime.block_on` block (added in 3b86d02). Don't drop these loops.
- **Group backfill routing precedence (§11.5)**: a backfill topic `group:<group_id>:backfill` ALSO passes `is_group_topic` (it starts with `group:`), so `handle_swarm_event` must check `is_backfill_topic` FIRST, then `is_group_topic`, then the broadcast path. `SubscribeGroup` subscribes the backfill topic and publishes `GroupBackfillRequest { group_id, after }` (`after` = `latest_group_sent_at`, max `sent_at`, `0.0` = full history); answering members re-publish bounded history (`load_group_messages_after`, strictly-greater `sent_at`, oldest-first, `MAX_MESSAGE_HISTORY` cap) on the MAIN topic, gated on `find_group` (never revive deleted groups) and `latest > after` (nothing to contribute → skip). Requests are control traffic — never persisted. Requester dedup = the normal `save_incoming_group_message` path.
- **Incoming group messages are persisted centrally by the swarm handler** (`swarm_handler::handle_group_message` → `groups::save_incoming_group_message`), so the DB is the single source of truth in both frontends. The mobile `group_message` swarm event only *notifies* the Flutter UI; `GroupChatScreen` reloads history from DB (no `save_incoming_group_message` FRB binding) and `GroupList` just refreshes counts — don't add per-screen persistence.
- **Group invites only carry a `group_id`, so materialize the group row**: `groups::ensure_group_for_invite` (used by `mobile_node::accept_group_invite`, and the TUI's GroupInvite arm which records membership then sends `SwarmCommand::SubscribeGroup`) creates the `groups` row with `display_name` = group_id when the canonical name isn't known. It is idempotent — reuses a row joined earlier by name.
- **Meshing group messages without an `msg_id` must still dedup**: `save_incoming_group_message` substitutes a stable synthetic key `nil:<fnv1a_hex(group_id|peer_id|sent_at|content)>` so SQLite's `(group_id, msg_id)` unique index (which treats `NULL`s as distinct) still stops retransmits. `GroupMessageMeta` stays as-is; the key is an internal `msg_id` on the row.
- **The caller mints the `call_id`; clients never guess one**: the TUI mints via `CallSession::outgoing`, the mobile/Flutter side mints Rust-side (`api::start_call` returns the fresh id). Every `CallSignal` echoes it (`CallSignal::new(kind, call_id)`); `CallSession::on_signal` mutates ONLY a matching-`call_id` session — stale/foreign ids are no-ops (the TUI's invite-adoption, the overlay transition, and Flutter's session filtering all rely on this). One call at a time everywhere (like the device-binding prompt/lane).
- **Call signaling is un-gated** (mirrors device-binding): `behaviour.rs` `call_signaling`, `types.rs` `SendCallSignal`, `calls.rs` `CallSession`/`CallState`, and both frontends ship without the `calls` Cargo feature — that feature stays reserved for future media deps. Don't gate signaling behind it.
- **Flutter call events key on `peer_id` + echoed `call_id` (`content`)**: `call_event_json` fills `event_type`/`peer_id`/`content`(call_id); `CallScreen` owns the event sink while open (like `DmChatScreen`, restored on dispose), filters on exactly those two, forwards non-call events downstream, and auto-declines (`reject`) a second incoming invite while one session is live. The mobile send path goes through FRB-exposed `api::{start_call, send_call_signal}` wrappers over `#[flutter_rust_bridge::frb(ignore)]` `mobile_node` impls that `cmd_tx.blocking_send` a `SendCallSignal` — same shape as device-binding.
- **Files lane (§12) is receiver-driven `request_response`** (`/p2p-chat/files/1.0.0`, cbor `FileTransfer`/`FileTransferResponse` with `kind` meta/chunk/error, `FILE_CHUNK_SIZE` 1 MiB, `MAX_ATTACHMENT_SIZE` 64 MiB). `file_id` = SHA-256 of the bytes (content address); blobs live on disk under `<db>.files` (never in SQLite — `files`/`files_recipients` tables). Messages carry only the `MessageAttachment` descriptor; group/broadcast attach **by reference** so gossipsub's 256 KiB cap stays unbroken. No feature gate (un-gated, like call signaling).
- **Attachment blob GC is gated by the `attachment-gc` Cargo feature** (in `default` and `mobile`): `swarm_handler::gc_stale_attachments()` sweeps `.part` partials of interrupted pulls (incomplete class) plus orphaned blobs/rows nothing references (the "overwritten"/superseded class, including blobs with no `files` row and rows whose blob vanished) — via `files::gc`/`files::GcStats`. Runs at startup in TUI (`main_loop.rs`) and mobile (`start_node_impl`), never touching in-flight transfers (active `file_id`s excluded) and honoring `files::GC_GRACE` (1 min blob age). The off-build is a `Ok(GcStats::default())` no-op — disabling the feature means the store never deletes anything. Sweeps run on startup only; a transfer interrupted mid-run keeps its `.part` until the next restart clears the in-flight map.
- **Both frontends render the canonical chip `[file] {name} ({size})`, with `{size}` produced by `files::format_file_size`** (`512 B`, `1.5 KiB`, `64 MiB` — binary units, one decimal max, trailing `.0` dropped): Rust `files::file_chip` / `render_message_body` / `render_stored_body` (hydrates DB `attachment_json` on reloads) format it, and Flutter's `_AttachmentChip` in `messages.dart` prints `MobileAttachment.sizeLabel`, which Rust fills from the same formatter — **no frontend does its own byte math**. Attachment-only messages render as just the chip. Mobile resolves blob paths exclusively through `attachment_file_path(file_id)`.
- **Flutter picks via `file_picker` 13.x — top-level `FilePicker.pickFile()`** (the `.platform` member was removed); opens via `open_filex` (`ResultType.done`/`result.message`). Both sit behind `pickFileOverride`/`openFileOverride` seams in `apps/flutter_app/lib/src/util/attachments.dart` — these are deliberately NOT `@visibleForTesting` because screens in other libraries call them (the annotation flags `invalid_use_of_visible_for_testing_member` cross-file, unlike the same-library seams in home/contact_list).
- **The web frontend is a display client, never a WASM node** (`docs/web_frontend.md`): `src/web/` (axum HTTP+WS) mirrors the FRB surface 1:1 as JSON methods; the `p2p_chat_server` binary runs the node in-process. Every new FRB-exposed fn needs a matching `src/web/methods.rs` arm, an entry in `src/web/mod.rs`'s no-param drift list (for zero-arg arms) and a `methods::dispatch(name, Null)` routing test asserting `invalid params:`. Build/run through `scripts/build-web.sh`.
- **TUI group leave** lives on the Groups tab: `d` arms `AppState.group_leave_prompt` (`begin_group_leave`), `y`/Enter confirms (`confirm_group_leave` → `groups::delete_group` + `SwarmCommand::UnsubscribeGroup`, closes the chat tab), any other key/Esc cancels. Popup precedence is `device_binding_prompt` > `group_leave_prompt` > call overlay > `popup`.
- **TUI local nicknames** (the name only this install shows for a peer) are edited with `n` on a **Peer Info** tab; that is distinct from the Settings-tab `n`, which edits our own nickname. Both go through `AppState::is_editing_nickname()`, which must keep covering `InputMode::EditingLocalNickname` as well as `InputMode::EditingNickname` — that mode (not a bool: `TuiRenderState` sits at clippy's `struct_excessive_bools` limit) is what tells the input-section title "Local Nickname (xxx)" from "Edit Nickname (xxx)". Submissions validate through the canonical `nickname::validate_nickname` and keep the editor open with a hint on bad input.
- **Contacts search is one matching rule, two implementations, one sort authority**: `state::contact_matches` (Rust) and `ContactListState._visibleRows` (Dart) both match a lowercased substring against the contact id, contact display name, and every device's peer id + display name — so a grouped user stays findable by a machine's peer id. Rust owns the rule; Flutter mirrors it because no FRB binding can filter a Dart list. **Filtering must happen before the Rust sort in both frontends** (TUI: `contacts` is the filtered view of `contacts_all`, re-derived by `apply_contact_search` inside `resort_peers`, never via a DB query per keystroke; Flutter: `_computeSorted` sorts only the visible subset and maps back against it), so a hidden row can never be returned by the comparator. TUI bindings: `/` opens the box, `Enter` keeps the query, `Esc` clears it; the box is checked **before** the Contacts `c`/`e`/`i` actions (`handle_contacts_action_key`) or typing those letters would place a call/expand a row. `InputMode::SearchingContacts` — do **not** add another `TuiRenderState` bool.
