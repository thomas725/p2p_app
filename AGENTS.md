Archived history (goal, done-index, decision rationale, backlog recap, descriptive

## Constraints & Preferences
- **Prefer nix tooling for anything not already installed as a system tool**: use `nix-shell` and similar nix tools (e.g. `nix-shell -p python3Packages.pyyaml`) whenever something isn't installed as a system tool. Do **not** reach for `podman`/`docker` for this — only use them if there is no nixpkgs package available for what's needed.
- Toolchain: **nightly** (`rustup override set nightly` in `/home/user/project`).
- All code must be clippy-clean with the project's strict pedantic config: `cargo ct` (alias for `cargo clippy --all-targets --all-features`) must exit 0 with no warnings.
- User decisions: peer click in Peers tab **keeps opening the DM tab**; message click in Chat/Log/DM **opens the sender's/partner's PeerInfo**.
- **Committing**: **always commit** once a logical block of work is done and it makes sense (commit early, commit often, as you work). Only **pushing** is reserved for the user.

## Code Rules (do/don't)
- **PeerInfo is a transient dynamic tab** (like DM), not a fixed tab: inserted after DMs, before Log/Settings. Dedup by peer ID.
- **PeerInfo binding is tab-specific**: plain `i` opens PeerInfo only on the **Peers** tab (no text input there). On **Direct/DM** tabs use `Ctrl+I` on kitty terminals (WezTerm) and `Ctrl+P` on every terminal. Bare Tab **always** cycles tabs on every tab and terminal. Shortcut bar only documents a binding where it is active.
- **Display-name memoization keeps the DB-backed resolution path**: don't swap the sort/render to in-memory nickname maps — `get_peer_display_name` caches the exact string it would compute (local → received → generated petname + short-ID suffix), so sort and render always agree. Invalidate exactly where nicknames change: `impl_set_peer_field!` setter macro and `peers::save_peer`; `db::set_db_url`/`reset_db_url` must keep calling `nickname::clear_display_names()`.
- **Warm the display-name cache lazily**, on the first frame that draws the Peers tab (`state.env.peer_names_warmed` in the render loop's draw closure), not at startup. Warm-at-startup was rejected.
- **The sort must never drop peers**: feed the whole `VecDeque` to `sort_peers_by_column` and rebuild via `HashMap<&str, PeerRecord>` — never `peers.as_slices().0` (a wrapped ring loses its second segment).
- **One canonical last-seen parser**: `fmt::parse_last_seen_ms` (space-or-T `%Y-%m-%dT%H:%M:%S`, 0 on failure) is the single source for both the TUI sort and the FRB/mobile wrapper — Dart never parses its own sort keys.
- **Keep TUI/Flutter sort parity**: Flutter sorts via Rust `mobile_api::sort_peers` (mirrors `tui_helpers::sort_peers_table`, ties on `peer_id`, descending reverses the whole `Ordering`). Don't regress to a Dart `List.sort` closure; keep `peer_list_test.dart`'s `_sortLikeRust` fake mirroring these exact semantics (lowercase name key, seen-column `parse_last_seen_ms` 0-on-failure, whole-ordering reversal).
- **`get_known_peers` (api wrapper) is a type anchor, not a live call path**: it is the only FRB-reachable reference to `MobilePeerRecord` (defined in the frb-ignored `mobile_node`). Deleting it makes the type vanish from the generated Dart and breaks `flutter analyze`. Keep it with a doc note pointing to the bulk call.
- **`apps/flutter_app/lib/src/rust/messages.dart` is a hand-maintained orphan** (`PeerMessageStats` isn't in FRB's `rust_input`; regen never touches it). Verify by hand after any change touching the peer-stats surface — including flipping the broadcast field to `broadcastSentToPeer`.
- **`broadcast_recipients` is the single per-peer "broadcast" source**: a broadcast *we* send is recorded once per connected peer (`record_broadcast_recipients`, idempotent), `confirmed_at` back-filled on ack. The "Broadcast" column uniformly means *broadcasts-sent-to-peer* in both frontends.
- **Migration version keys are the date+time, NOT the directory stem**: two migrations sharing a timestamp (`000000`) collide silently. Use distinct suffixes (`...000000_...` / `...000001_...`).
- **Stateful table windowing**: ratatui's `Table` + `TableState` is the "widget that allows scrolling visually" — it keeps the selected row visible. `tui_helpers::peer_table_visible_range` is the pure reimplementation that the click handler and renderer both agree on; keep them consistent.
- **Saved groups must be re-subscribed on node start** in BOTH frontends: the swarm only receives group traffic for topics it is subscribed to. TUI does it in `main_loop.rs` after `spawn_swarm_handler`; mobile does the same inside `mobile_node::start_node_impl`'s `runtime.block_on` block (added in 3b86d02). Don't drop these loops.
- **Group backfill routing precedence (§11.5)**: a backfill topic `group:<group_id>:backfill` ALSO passes `is_group_topic` (it starts with `group:`), so `handle_swarm_event` must check `is_backfill_topic` FIRST, then `is_group_topic`, then the broadcast path. `SubscribeGroup` subscribes the backfill topic and publishes `GroupBackfillRequest { group_id, after }` (`after` = `latest_group_sent_at`, max `sent_at`, `0.0` = full history); answering members re-publish bounded history (`load_group_messages_after`, strictly-greater `sent_at`, oldest-first, `MAX_MESSAGE_HISTORY` cap) on the MAIN topic, gated on `find_group` (never revive deleted groups) and `latest > after` (nothing to contribute → skip). Requests are control traffic — never persisted. Requester dedup = the normal `save_incoming_group_message` path.
- **Incoming group messages are persisted centrally by the swarm handler** (`swarm_handler::handle_group_message` → `groups::save_incoming_group_message`), so the DB is the single source of truth in both frontends. The mobile `group_message` swarm event only *notifies* the Flutter UI; `GroupChatScreen` reloads history from DB (no `save_incoming_group_message` FRB binding) and `GroupList` just refreshes counts — don't add per-screen persistence.
- **Group invites only carry a `group_id`, so materialize the group row**: `groups::ensure_group_for_invite` (used by `mobile_node::accept_group_invite`, and the TUI's GroupInvite arm which records membership then sends `SwarmCommand::SubscribeGroup`) creates the `groups` row with `display_name` = group_id when the canonical name isn't known. It is idempotent — reuses a row joined earlier by name.
- **Meshing group messages without an `msg_id` must still dedup**: `save_incoming_group_message` substitutes a stable synthetic key `nil:<fnv1a_hex(group_id|peer_id|sent_at|content)>` so SQLite's `(group_id, msg_id)` unique index (which treats `NULL`s as distinct) still stops retransmits. `GroupMessageMeta` stays as-is; the key is an internal `msg_id` on the row.

- **Dependency audit config**: `.cargo/audit.toml` is comment-only — the hickory
  `RUSTSEC-2026-0118`/`0119` ignores were retired on 2026-09-20 (**libp2p 0.57.0**, `fb65264` →
  libp2p-mdns 0.49.0 → hickory-proto 0.26.3, past the 0.26.1 fix line). `cargo audit` is clean
  (exit 0); the one remaining row is the unmaintained `paste` 1.0.15 (RUSTSEC-2024-0436, a
  build-time proc-macro from `libp2p-mdns → if-watch → netlink-packet-core` — benign, core libp2p).
  CI dependency job gates on `cargo audit` (hard fail) + artifact upload; `cargo outdated` is
  informational.

- **Scheduled-workflow skip checks need `actions: read`**: `.github/workflows/dependencies.yml` and `nightly-apk.yml` run `scripts/ci-skip-no-new-commits.sh`, which queries the Actions runs API with the GITHUB_TOKEN. The token must carry `actions: read`, or that endpoint returns 403 and (previously, fail-open) every nightly run executed anyway — producing duplicate `ci: refresh coverage and codebase metrics` commits on main. The script is fail-closed now: any API error skips the run (a manual `workflow_dispatch` overrides). Don't drop that permission when editing the workflows.
- **Metrics skip-check uses commit-baseline mode**: `.github/workflows/metrics.yml` calls `scripts/ci-skip-no-new-commits.sh metrics.yml --commit-baseline="ci: refresh coverage and codebase metrics"`. The baseline is the newest CI-authored commit matching that subject on the branch (resolved by local git, no API call), NOT the last workflow run — so a skipped run can never become the baseline and reseed the "no commits at all" skip loop. Only the metrics workflow uses this mode; the other two stay on run-history mode.
