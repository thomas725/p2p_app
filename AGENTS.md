## Goal
- Fix broken TUI click handlers (peer-click bug + missing message-click) and port the Flutter `PeerInfoScreen` into the TUI as a new PeerInfo tab.
- Adapt the TUI peer list to mirror Flutter's sortable peer table (columns Name, DM count, Broadcast count, Last seen; each sortable by key or header click).
- Make the TUI Peers tab scrollable with PageUp/PageDown (plus Home/End), show a total peer count, and use ratatui's stateful `Table` widgets so the viewport scrolls visually while keeping the selected row visible.
- Fix Peers-tab sluggishness with many peers (per-frame SQLite nickname lookups per row) by materializing only the visible window of rows, and remove the "Peers: N" bar between the tab bar and tab content.
- Make switching the Peers-tab sort column fast (it did one fresh-SQLite display-name lookup per peer on every full-list sort) by memoizing `get_peer_display_name`, warming the cache lazily the first time the Peers tab is opened, and making the sort reorder O(n).

## Constraints & Preferences
- Toolchain: **nightly** (`rustup override set nightly` in `/home/user/project`).
- All code must be clippy-clean with the project's strict pedantic config: `cargo ct` (alias for `cargo clippy --all-targets --all-features`) must exit 0 with no warnings.
- User decisions: peer click in Peers tab **keeps opening the DM tab**; message click in Chat/Log/DM **opens the sender's/partner's PeerInfo**.

## Key Decisions
- Ratatui's stateful `Table` + `TableState` is the official "widget that allows scrolling visually" — it scrolls to keep the selected row visible. `peer_table_visible_range` reimplements its windowing as a pure function so (a) unit tests run without a widget, (b) the click handler and renderer agree on the visible window, and (c) `AppState.peer_table_offset` serves as the anchor fed into windowing each render. Verified against the ratatui 0.3.2 source: `render_stateful_widget` mutates `TableState.offset` in `render_rows` (`state.offset = start_index`) and reads it in `visible_rows`.
- **The originally "failing" render test was a bogus assertion, not a scroll bug**: `test_render_peers_scrolls_viewport_but_keeps_selection_visible` failed because display-name cells are **truncated to the name column width** in the buffer (`organic-rockhopper (pee…`), so `text.contains("peer-29")`/`contains("peer-00")` can never hold. The scroll actually worked (verified by mapping petnames→row indexes: rendered rows 10..29). Rewrote the test to give each peer a distinct `last_seen` second (`15:26:{i:02}`) and assert `contains("15:26:29")`, `!contains("15:26:00")`, exactly 20 visible rows, and the `Connected Peers (30)` title.
- **Diesel `table!` unit structs are handled by module-ignore, not an FRB upgrade**: the panic is a long-standing FRB limitation (identical reports from FRB 2.1.0–2.3.0; the maintainer's standing reply is "feel free to PR"), so upgrading FRB alone would not fix codegen. The working fix marks the whole `generated` module (now hosting every diesel table in the crate, incl. the relocated `peer_name_history`) with `/// flutter_rust_bridge:ignore`; both 2.12.0 and 2.13.0 then generate cleanly. The user still chose to bump **2.12.0 → 2.13.0**.
- PeerInfo is a **transient dynamic tab** (like DM), not a fixed tab: inserted after DMs, before Log/Settings. Dedup by peer ID.
- Click row→message mapping reuses library helpers; `calc_visible_strings` returns `(visible, start)` where `start` is the first visible message index (for auto-scroll it equals `total - visible`), used to map the relative row back to the absolute message index.
- `terminal_width` stored on `AppState` (set in render loop via `usize::from(f.area().width)`) so click mapping matches wrapping; default 0 treated as width 1 (only before first render).
- **PeerInfo binding is tab-specific**: plain `i` opens PeerInfo only on the **Peers** tab (where there is no text input), so `i` stays typeable in the Chat/DM message boxes. On **Direct/DM** tabs the binding is **Ctrl+I** on kitty terminals (WezTerm, `AppState.kitty_keyboard_active` true from crossterm's `supports_keyboard_enhancement()`) — arriving as `Char('i')`+CONTROL — and **Ctrl+P** (`Char('p')`+CONTROL, from `0x10` DLE) on **every** terminal: on non-kitty terminals it is the only Peer Info binding (both Ctrl+I and Ctrl+Shift+I collapse to the bare `0x09` Tab byte there), and on kitty terminals it is a bonus fallback alongside Ctrl+I. Bare Tab always cycles tabs on every tab and terminal, in both modes. `Tab`+CONTROL (an alternate CSI-u spelling of Ctrl+I a conforming terminal should never send in practice) is a no-op everywhere including Direct tabs. The bottom shortcut bar only documents the binding where it is active (kitty Direct tabs show both `Ctrl+I/Ctrl+P`).
- **Display-name memoization keeps the DB-backed resolution path**: the cache stores the exact string `get_peer_display_name` would compute (local → received → generated petname, with the short-ID suffix), so the sort and the rendered table always agree — including the lazy petname **write** for silent peers that only exists on the DB path (swapping the sort to the in-memory nickname maps would have made names inconsistent with the render). Staleness is prevented by invalidating exactly where nicknames change: the `impl_set_peer_field!` macro (all peer-nickname setters) and `peers::save_peer` (may assign a petname to a brand-new peer).
- **Warm the cache lazily on first Peers-tab open, not at startup** (user-chosen): the one-time N-lookup cost is deferred to the first frame that draws the Peers content (`AppState.peer_names_warmed` set inside the render loop's draw closure). Zero cost if the user never opens the Peers tab; later-discovered peers warm on demand (one cache miss each). Warm-at-startup (Flutter-style eager `_refreshPeers`) was offered but rejected to avoid a boot-time tax on large peer lists.
- **The sort must never drop peers**: feeding `peers.as_slices().0` into `sort_peers_table` loses every peer in the wrapped (second) ring segment — `peers.as_slices().0` is the *head..cap* range (`[1,2,3]` for a wrap where element 8 sits at buf[0], e.g. fill-8/pop-1/push-1). `sort_peers_by_column` therefore iterates the whole `VecDeque` and rebuilds from a `HashMap<&str, PeerRecord>`.
- **One canonical last-seen parser**: `parse_last_seen_ms` lives in `src/fmt.rs` (space-or-T `%Y-%m-%dT%H:%M:%S`, 0 on failure) and is the single source for both the TUI sort comparator (via `crate::fmt::`) and the FRB/mobile wrapper — Dart therefore never needs its own `DateTime.tryParse` for sort keys. The FRB wrapper uses `#[frb(sync, type_64bit_int)]` so Dart gets a 64-bit `int` instead of `BigInt`, matching the `is_at_bottom` precedent.
- **Mobile sort parity beats Dart's unstable sort**: `mobile_api::sort_peers` mirrors `sort_peers_table`'s column mapping and ties on `peer_id`, so Dart replacing its `List.sort` closure (unstable on ties) with the Rust call is strictly deterministic. Descending reverses the *whole* `Ordering` (ties swapped too) on both sides, so TUI and Flutter sort identically.
- **`get_known_peers` (api wrapper) is a type anchor, not a live call path**: FRB only generates a type into the Dart surface if some non-`#[frb(ignore)]` function references it. `MobilePeerRecord` (defined in `mobile_node`, which is frb-ignored) is only reachable through the `api::get_known_peers` wrapper — so even though Flutter's peer table now prefers `getPeersWithStats`, the wrapper must stay or `MobilePeerRecord` vanishes from the generated Dart and `flutter analyze` breaks (undefined class in PeerInfoScreen/`_refreshPeers`). Keep it with a doc note pointing to the bulk call.
- **`apps/flutter_app/lib/src/rust/messages.dart` is a hand-maintained orphan, not FRB-generated output**: `PeerMessageStats` lives in `src/messages.rs`, which is NOT in FRB's `rust_input` (`crate::api,crate::mobile_api,crate::mobile_node`), so FRB never (re)generates the `PeerMessageStats` Dart class — `src/frb_generated.rs` has NO `PeerMessageStats`, and regen leaves `messages.dart` untouched. After dropping the dead `broadcast_sent` field, the file had to be **hand-edited** to remove `broadcastSent` (the 2.13.0 regen didn't do it, in contrast to `mobile_api.dart`/`frb_generated.dart`/`frb_generated.rs`, which ARE regenerated). Worse, `messages.dart` was actually regenerated in an earlier session only because `PeerMessageStats` was once FRB-reachable — its classification flips between "generated" and "orphan", so it must be verified by hand after any regen/refactor that touches the stats surface. This is the same orphan class as the now-deleted `types.dart`.
- **The outbound `broadcasts_sent` counter is a dormant write-only signal, kept for the mobile write path**: it cannot be recomputed from message history (history doesn't record which peers were connected at send time), and it now feeds no UI column (both frontends' "Broadcast" column read `broadcast_received`). It remains incremented at send time (`mobile_node::save_outgoing_broadcast` → `peers::record_broadcasts_sent`) and persisted in `peers.broadcasts_sent`, but nothing reads it back — a deliberate, documented dead-write reservation rather than either removing the write (untestable mobile path) or schemas/migration.
